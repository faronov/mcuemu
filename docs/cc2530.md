# TI CC2530F256

`mcs51emu::Cc2530F256` (`emulator/src/mcs51/cc2530f256.cpp`) is a CC2530F256
SoC model around the generic `UC_ARCH_MCS51` core. Register semantics follow TI
SWRU191F (CC253x/4x User's Guide); the protected flash pages follow the
`cc2530-zigbee` firmware contract (`docs/BANKED_CODE.md` in that repository).
All CC2530 facts live in the SoC model: the core and memory map in
`cc2530f256.cpp`, the peripherals in `emulator/src/mcs51/cc2530_*.cpp`. The
MCS51 core only gained generic, default-preserving registers (see "Core
options" below). Each peripheral source file starts with a model summary and
marks every rule SWRU191F leaves open as "Model-defined"; those comments are
the authoritative list of approximations.

## Running

```sh
./build/mcuemu run --model CC2530F256 --firmware image.hex --steps 1000000 \
  [--trace] [--state] [--until-pc 0x1234 [--hits N] [--report-hits] \
  [--write-xdata 2:0x0400:4ab5]] [--dump-xdata 0x0200:16] \
  [--ieee-address 0x00124b0001020304] [--program-via-debug-if [--debug-lock]]
```

Intel HEX addresses are physical flash addresses: bank N starts at
`N * 0x8000`, given by type 02 or type 04 extended address records
(`llvm-objcopy -O ihex` emits type 02 below 1 MiB). A raw binary starts at
physical address 0. ELF files are rejected; convert them with
`llvm-objcopy -O ihex`, which uses the load addresses. Programming flash at or
above `0x3e800` (the firmware's NV pages and the lock page) loads but is
reported as a load warning.

The run stops at the step limit, a fault, a power mode from which nothing can
wake the chip (no queued event, pending reset or peripheral that may still
raise an interrupt), `--until-pc` (before that instruction executes) or an idle
self-loop (`SJMP $`, `AJMP` or `LJMP` to itself) with no deliverable interrupt
and no peripheral that may raise one. Time spent in a power mode advances the
cycle count but not the instruction count. The runner checks for the idle
loop between 100000-instruction slices, so the reported instruction and cycle
counts include the spin in the final loop. `--state` prints the core
registers, MEMCTR and MPAGE (`core:` line, DPTR there is DPTR0), then a
`cpu-ext:` line with DPTR1, DPS, the in-progress interrupt level mask, the
post-RETI inhibit and the posted vector; the runner always prints the physical flash
address of the PC, interrupts taken and the access diagnostics (unmodeled XREG
reads and writes per address, unmapped XDATA accesses, writes to read-only
registers). The full `Cc2530Diagnostics` (unmodeled peripheral features,
power-mode, reset and stall statistics) is available to C++ callers. `--state` also prints IDATA and every SFR (`sfr 0x80..0xff`
lines, read side-effect free).

`--hits N` continues past `--until-pc` until its N-th arrival there (an
arrival is a stop before that instruction; the first instruction of the run,
at the reset vector, is never one). `--report-hits` prints a `hit: K` line
with instructions, cycles, PC, SP, DPS, FMAP and the interrupt level mask at
every arrival, followed by the `--state` and `--dump-xdata` memory at that
point and `end-hit: K`. `--write-xdata HIT:ADDR:HEX` (repeatable) stores the
bytes to XDATA SRAM at `ADDR` on arrival `HIT`, after that arrival's report,
the way a host writes a mailbox while the firmware is halted at a checkpoint.
The summary reports `until-pc-hits`.

`--program-via-debug-if` starts from an erased chip and programs the image
through the [debug interface](#debug-interface) the way a CC Debugger does,
then releases RESET_N and runs it; `--debug-lock` also programs DBGLOCK = 0.
Two extra lines report the chip ID, the pages written, the bytes verified,
the debug commands and the cycle span, and whether the flash matches the
image (exit code 1 if not). The run that follows starts at that cycle count.

In a system file the model is `cc2530f256` (default `clock_hz` 32 MHz). It has
no variants. Pads `P0.0`-`P2.4` connect to nets, as does the input-only
`RESET_N` pin (low holds the chip in reset; a floating net counts as high,
model-defined), `uart0`/`uart1` are USART0/1
in UART mode, USART SPI master and slave run on the pads (see
[USART SPI](#usart-spi)), `supply_mv` (2000-3600, default 3300) is the AVDD seen
by the ADC, and `radio:` attaches the IEEE 802.15.4 radio (`zigbee` only, at
the default 32 MHz). The standalone `mcuemu run` model uses VDD = 3000 mV. `debugger:` emulates a host that halts at a checkpoint
and writes XDATA (see [system-config.md](system-config.md)); it is not the
chip's [debug interface](#debug-interface), which the RPC methods
`debug_if.*` drive (see [control-api.md](control-api.md)). `read_memory` (RPC `mem.read`)
uses one 32-bit window per 8051 space:

| Address | Content |
| --- | --- |
| `0x0000_0000`-`0x0000_ffff` | CODE as the CPU sees it now (FMAP/XMAP applied) |
| `0x0001_0000`-`0x0001_ffff` | XDATA, side-effect free (XREGs read as latched) |
| `0x0002_0000`-`0x0002_00ff` | DATA/IDATA (also XDATA `0x1f00`-`0x1fff`) |
| `0x0003_0080`-`0x0003_00ff` | SFRs |
| `0x0004_0000`-`0x0004_003f` | CPU snapshot (layout in `sim/cc2530f256_mcu.hpp`) |
| `0x0100_0000`-`0x0103_ffff` | physical flash |

`write_memory` (`mem.write`) accepts XDATA SRAM and IDATA only. An idle self-loop puts the
MCU in `Halted`, a power mode with no possible wake source (nothing inside the
chip and nothing external connected: nets, air, UART) in `Sleeping`, and a CPU
exception or unsupported behaviour in `Fault`, each with a message giving the
PC and bank. `Sleeping` and `Halted` are final for that run.

## Memory

CODE has three identities that must not be confused: the linker's virtual
address, the 16-bit CPU logical address and the physical flash offset.

- Logical CODE `0x0000`-`0x7fff` is always physical bank 0.
- Logical CODE `0x8000`-`0xffff` shows bank `FMAP` (`0x9f`, reset value 1):
  physical `FMAP * 0x8000 + (logical - 0x8000)`. All eight banks are valid on
  the F256; FMAP bits 7:3 read as 0.
- With `MEMCTR.XMAP` (`0xc7` bit 3) set, logical `0x8000`-`0x9fff` is the
  8 KiB SRAM; the rest of the upper half keeps showing the FMAP bank.

The model keeps one 64 KiB view per FMAP value and repoints the core's direct
CODE pointer (`UC_MCS51_REG_FAST_MEMORY`) when FMAP or XMAP changes, so the
very next fetch uses the new mapping. No translated code needs to be flushed:
the interpreter decodes the bytes behind that pointer, and translation blocks
only size one instruction. The XMAP view's lower 8 KiB *is* the SRAM buffer,
so code written to SRAM and executed through XMAP is always coherent.

XDATA:

| Range | Content |
| --- | --- |
| `0x0000`-`0x1fff` | SRAM (`0x1f00`-`0x1fff` is also DATA/IDATA) |
| `0x2000`-`0x5fff` | unimplemented; reads 0, counted |
| `0x6000`-`0x63ff` | XREGs: radio RAM `0x6000`-`0x617f` and radio registers from `0x6180`, flash controller `0x6270`-`0x6273`, DBGDATA `0x6260` (read-only, loaded by BURST_WRITE), the other peripheral XREGs (owned by their models); CHVER, CHIPID (`0xa5`), CHIPINFO0/1 read-only; XREGs no model owns are counted latches |
| `0x6400`-`0x707f` | unimplemented; reads 0, counted |
| `0x7080`-`0x70ff` | SFR alias; 8051-internal SFRs are not mapped (P0-P2 read-only) |
| `0x7100`-`0x77ff` | unimplemented; reads 0, counted |
| `0x7800`-`0x7fff` | information page, read-only; IEEE address at `0x780c` (`--ieee-address`) |
| `0x8000`-`0xffff` | flash bank `MEMCTR.XBANK`, read-only, independent of FMAP |

`MOVX @Ri` takes its high address byte from MPAGE (`0x93`), not P2. The
hardware stack and register banks are the usual 8051 ones in IDATA (SP resets
to 7).

## Interrupts, clock and power

The 18 sources of SWRU191F Table 2-5 are modeled as flags and enables, with
vector `0x03 + 8 * n`, the six priority groups IPG0-IPG5 with four levels
from IP1/IP0 (level = `IP1.g:IP0.g`), the polling order of Table 2-8 within a
level, `EA` gating, and the hardware flag clear on vectoring for the sources
that have one. Peripherals raise their CPU flags through the same path as
firmware writes. The port interrupt flags `P0IF`/`P1IF`/`P2IF` follow
`PxIFG & PxIEN` as a level and are re-asserted when firmware clears the CPU
flag while `PxIFG` is still set, so `PxIFG` must be cleared first (SWRU191F
2.5.1, 7.4). Timer 1/3/4 set their CPU flag on events and when a status flag
is cleared while others remain (SWRU191F 9.10, 10.6). `IRCON` bit 6 "Must be
written 0. Writing a 1 always enables the interrupt source" (SWRU191F 2.5.1);
Figure 2-4 ORs it with STIF into the sleep timer request ahead of STIE and
EA, and it is not cleared on vectoring, so a 1 requests the ST interrupt (and
wakes PM0-PM2 like STIF) until firmware writes it 0. Such writes are counted
in `ircon_bit6_writes`.

Interrupts nest by level (SWRU191F 2.5.3): a request is taken at an
instruction boundary when no ISR is in progress or its level is higher than
every level in progress; an equal or lower level waits. The highest pending
level wins, ties go by Table 2-8. Entry pushes the PC (LCALL to the vector)
and marks the level in progress; RETI ends the highest level in progress. After
RETI exactly one more instruction executes before any interrupt is taken
(8051 RETI semantics), so a still-pending source re-enters only after that
instruction. Priority, enable, EA and flag writes are re-evaluated at the next
boundary. The model is instruction-granular: an entry costs the 7-cycle
minimum response of SWRU191F 2.5.2 (see the timing contract), and flag
sampling phases are not modelled.

### Interrupt-delivery contract

Every change to an interrupt flag, enable or priority SFR, whether by
firmware, host, test hook or scheduled event, goes through `sfr_write()` /
`set_interrupt_flags()` and `update_interrupts()`, which post the resulting
request (vector and level) to the core. The posted request is evaluated at
every instruction boundary in every execution mode:

- trace mode: the per-instruction code hook applies due events and re-checks
  the request before each instruction;
- single steps and the `run()` loop: due events are applied and the request
  re-checked at each boundary at which the loop regains control, and at the
  closing boundary of every `run()` call;
- fast mode: the core stops at the first boundary at which the next scheduled
  event or peripheral deadline is due (`UC_MCS51_REG_EVENT_CYCLES`; a register
  access that moves a deadline earlier lowers the stop), at the posted vector,
  and whenever `update_interrupts()` changes the request during a translated
  block (`uc_emu_stop`), so a request is never delayed past the boundary at
  which it became eligible.

`Cc2530Diagnostics::stale_interrupt_posts` counts boundaries at which the
posted request differed from the one recomputed from the SFRs (a change that
bypassed `update_interrupts()`); it must stay 0.

### Peripheral scheduler and virtual-time test events

Peripherals own their SFRs and XREGs (`claim_sfr`/`claim_xreg` in
`cc2530_soc.hpp`); CPU, DMA and host accesses are dispatched to the owner, and
`mem.read` uses the owner's side-effect-free peek. A peripheral does not run
per instruction: it reports the next cycle at which it has something to do
(`deadline()`), and the core services it at the first instruction boundary
whose cycle count is `>= deadline`, in every execution mode. Peripherals
compute their state in closed form between deadlines, so an event is
processed with its own timestamp whatever the run mode. Test events (below)
come first at equal times, then peripherals in construction order. Clock
(`CLKCONSTA`) and power-mode changes are broadcast to all peripherals.

C++ tests can also inject CPU interrupt flags directly:

`Cc2530F256::raise_interrupt_flag_for_test` sets a Table 2-5 CPU flag
immediately, exactly as a firmware write would, and counts it in
`test_injected_flags`. `schedule_interrupt_flag_for_test(at_cycle, source[,
mask])` queues the same flag change for virtual time `at_cycle`; events are
applied in (time, scheduling order) at the first instruction boundary whose
cycle count is `>= at_cycle`, independently of firmware SFR writes, and
counted in `scheduled_flag_events`. `scheduled_event_count()` and
`next_event_cycle()` expose the queue. For ENC (`S0CON` bits 0/1) and RF
(`S1CON` bits 0/1) the mask selects `ENCIF_0`/`ENCIF_1` and
`RFIF_0`/`RFIF_1`; the CPU request is their OR (SWRU191F 2.5.2, S0CON/S1CON:
"Setting one of these flags requests interrupt service"). These hooks are
not reachable from the system layer, JSON-RPC or MCP and do not pretend that
a timer, DMA or radio generated the event.

DPS (`0x92`) bit 0 selects DPTR0 (`0x82`/`0x83`) or DPTR1 (`0x84`/`0x85`) for
`MOV DPTR,#`, `INC DPTR`, `MOVX @DPTR`, `MOVC @A+DPTR` and `JMP @A+DPTR`;
both pointers are independent SFRs and reset to 0. DPS bits 7:1 read as 0.

`CLKCONCMD` is mirrored to `CLKCONSTA` immediately, with no oscillator
start-up time: the 16 MHz RC oscillator (`OSC = 1`) limits TICKSPD and CLKSPD
to 16 MHz, and a TICKSPD faster than CLKSPD shows, and runs, at CLKSPD
(SWRU191F 4.4). Peripherals count the HF tick `32 MHz >> TICKSPD` and the
32 kHz domain from the virtual cycle count. The CPU instruction rate is not
slowed by CLKSPD or the RC oscillator: one cycle is always 1/32 MHz, and
`clock_hz` (32 MHz with a radio) converts cycles to world time. `SLEEPSTA`
shows CLK32K toggling with the 32 kHz domain, the latched reset cause and
OSC32K_CALDIS, and, as the standard Z-Stack HAL expects, the oscillator-stable
flags of the older SLEEP register: XOSC_STB (bit 6) and HFRC_STB (bit 5), set
unless `stop_oscillator` stopped that oscillator. SWRU191F does not list them;
Z-Stack's `HalMcuInit` polls bit 6 after `SLEEPCMD &= ~OSC_PD` and would hang
forever without it (the DIYRuZ Motion Router image did). The start-up time is
not modelled. `examples/cc2530_zigbee.yaml` runs that image against the
TLSR8258 coordinator.

### Timing contract (model-defined)

The model selects the core's TI cycle model
(`UC_MCS51_REG_CYCLE_MODEL = UC_MCS51_CYCLE_MODEL_CC253X`), so every opcode
takes the "Cycles" count of SWRU191F Table 2-3 (for example `INC DPTR` 1,
`MOV direct,#data` 3, `MOV Rn,direct` 4, `MOVX A,@DPTR` 3, `MOVX @DPTR,A` 4,
`LCALL` 6, `RETI` 4, `MUL AB`/`DIV AB` 5). An interrupt entry takes 7 cycles,
the fastest response of SWRU191F 2.5.2 (one cycle to detect the request and
six for the forced LCALL), and counts as one instruction in `instructions`.
The classic table stays the core default, so the CA51F253L3 is unchanged.
`cc2530emu-r2-tests` (T0) checks every defined opcode against an independent
transcription of Table 2-3 (`tests/mcs51/cc2530_table_2_3.hpp`, with the
data-sheet line of each row) and T0b checks the entry cost, in fast and trace
mode. Peripheral timing (timers, DMA, flash, AES, USART, radio) is exact
against the virtual cycle count.

Model-defined rules and remaining approximations:

- Table 2-3 counts are the best case: SWRU191F notes that they assume
  single-cycle access to the memory operand and that flash reads may take
  1-3 cycles. Flash wait states, flash prefetching (`FCTL`), the flash cache
  (`MEMCTR.CACHDIS`) and fetch alignment (2.1) are not modelled; no memory
  access stalls the CPU except the flash controller's erase/write stall.
- A conditional jump (`JZ`, `JC`, `JB`, `CJNE`, `DJNZ`, ...) takes the single
  count of the table whether or not it jumps.
- The entry is always exactly 7 cycles and is taken at an instruction
  boundary: a request arriving during an instruction waits for its end, and
  that wait is not part of the 7 cycles. SWRU191F states only the minimum
  ("depending on current instruction"); the model adds no longer response.
  The one-instruction-after-RETI rule (8051 semantics) is kept. SWRU191F does
  not state the classic 8051 extra delay after a write to IE/IP, so it is not
  modelled: enable and priority writes are re-evaluated at the next boundary
  (the 2.5.2 note that the CPU may still enter an ISR right after
  `XCH A,IEN0` clears EA is not reproduced).
- The CPU is not slowed by CLKSPD or the RC oscillator (one cycle is always
  1/32 MHz).
- Table ambiguities resolved from the opcode map: `DJNZ Rn,rel` is listed as
  1 byte (it is 2), `DIV A` is `DIV AB`, `JNC` shows no operand (`JNC rel`),
  and `XRL direct,#data` sits after a page break; their cycle counts are used
  as printed.

The model is therefore not cycle accurate: software delay loops, interrupt
latency and the interleaving of CPU accesses with peripheral events follow
the best-case counts.

### Power modes (PCON.IDLE, SLEEPCMD.MODE)

Writing `PCON.IDLE = 1` enters the mode selected by `SLEEPCMD.MODE` (SWRU191F
4.1, 4.3): IDLE (PM0), PM1, PM2 or PM3. In a power mode no instruction
executes; virtual time advances to the next event or peripheral deadline
(counted in `idle_cycles` and per mode in `power_mode_cycles_by_mode`). The
mode takes effect at the boundary after the PCON write. Wake rules
(model-defined from SWRU191F 4.1):

- IDLE: any posted request, i.e. `EA` set and a source enabled with its flag
  set, whatever its priority (SWRU191F does not say whether a
  priority-blocked request wakes PM0);
- PM1/PM2: `EA` plus enable and flag of P0INT, P1INT, P2INT or the sleep
  timer (ST; the ST request includes `IRCON` bit 6);
- PM3: `EA` plus enable and flag of P0INT, P1INT or P2INT;
- a reset ends any mode.

The HF clock domain (Timers 1, 3 and 4, MAC timer, DMA, flash, AES, USART,
radio) is frozen in PM1-PM3; the sleep timer runs in PM0-PM2 and stops in PM3.
The watchdog counts in active mode and IDLE and holds its count in PM1-PM3:
SWRU191F 16 says the counter is "retained during all power modes" and
"continues counting when entering active mode again", and 4.1.3 does not
list the WDT among the blocks active in PM2 although its 32 kHz clock runs
there (Table 4-1), so it cannot reset or interrupt in PM1-PM3. Model-defined:
counting resumes at the next 32 kHz period boundary after the wake. AES registers, key and IV return to reset values on
PM2/PM3 entry. A request that already satisfies the wake rule at the PCON
write wakes the CPU at once (`power_mode_immediate_wakes`), so the outcome
does not depend on whether the request arrives just before or just after the
write. After every wake the instruction following the PCON write executes
before any interrupt is taken (SWRU191F 4.2; the 4-byte alignment requirement
is only counted in `idle_alignment_violations`). The wake happens at the
boundary where the request is posted, including the closing boundary of a
`run()` call, so a stop never shows a sleeping core with a posted request.
After PM1-PM3 the chip resumes at once on the commanded clock; the RC
oscillator period while the XOSC restarts is not modeled. With nothing that
can wake it the run stops asleep.

### Clock loss (CLD, stop_oscillator)

The emulated oscillators never fail on their own. A host declares one
stopped, as with a damaged crystal, with
`Cc2530F256::stop_oscillator(osc, at_cycle)` or, in the system layer,
`Cc2530F256Mcu::stop_oscillator(osc, at_ns)` (world time, rounded up to a
cycle). `osc` is `Xosc32M`, `Rcosc16M`, `Xosc32k` or `Rcosc32k`. The stop
takes effect at the first instruction boundary at or after that time, in
every execution mode, and lasts until the model is powered on afresh (a
firmware load, `Cc2530F256::power_on_reset()` or `Cc2530F256Mcu::reset()`).
Model-defined: `power_cut()` keeps it, as a damaged crystal stays damaged
when the supply returns. There is no YAML, JSON-RPC or MCP endpoint for it.

With `CLD.EN = 1` (SWRU191F 5.2) the 32 MHz XOSC and the 32 kHz clock
monitor each other; when one stops toggling, a clock-loss reset
(`SLEEPSTA.RST = 11`) follows within 0.25 ms (32 MHz XOSC) or 0.5 ms (32 kHz
clock). In PM1/PM2 the detector is stopped and restarts when the clocks
start again. Model-defined where SWRU191F is silent:

- the reset comes exactly at the maximum time-out (8000 or 16000 cycles)
  after the later of the stop and the start of monitoring (`CLD.EN` 0 -> 1, a
  new oscillator selection in `CLKCONCMD`, the wake from PM1-PM3);
- the XOSC is watched while `CLKCONCMD.OSC` selects it (5.2: "It is assumed
  that the 32-MHz XOSC is selected as system clock source"), and the 32 kHz
  clock is the source `CLKCONSTA.OSC32K` selects; the 16 MHz RCOSC is not
  watched;
- PM3 with `CLD.EN = 1`, which 5.2 tells firmware to avoid, is treated like
  PM1/PM2 and counted in `clock_loss_pm3_entries`.

Without a clock-loss reset, a stopped oscillator has its SWRU191F 4.4
consequences: the CPU waits for a stopped system clock (`clock_stalled()`,
counted in `clock_stall_cycles`) until a reset, for example from the
watchdog, which runs on the 32 kHz clock; a stopped 32 kHz clock stops the
sleep timer and the watchdog; and a `CLKCONCMD` switch to a stopped oscillator
never completes, because the source changes only once the new one is stable.
After a wake from PM1-PM3 the chip resumes on the 16 MHz RCOSC when the
XOSC is stopped. Model-defined approximation: peripherals clocked by the
system clock keep counting virtual time while the CPU stalls.

The radio keeps events on the HF clock (32 cycles per microsecond, one symbol
= 512 cycles). The air payload is the MPDU without its FCS; the receiver
appends RSSI (offset 73 dB) and a fixed correlation value of 110 when AUTOCRC
is set. While searching for an SFD the receiver polls the air every 160 us
(model-defined), so a frame registered before it starts is found before its
SFD completes.

RSSI is averaged over 8 symbol periods (128 us; SWRU191F 23.10.3, RSSI
register) and `RSSISTAT.RSSI_VALID` is set 8 symbol periods after the
receiver is enabled. Model-defined, since SWRU191F gives no update rate: a
new average is taken every symbol period (16 us) from the RSSI_VALID instant
on, over the 8 symbol periods before it, as the exact time integral (in mW)
of the received power, which is the strongest of the frames in flight on the
channel or the noise floor. `ENERGY_SCAN = 1` shows the peak of these
samples since the 0 -> 1 write. CCA is "updated at every new RSSI sample"
and four system clock cycles after RSSI_VALID (23.8.12), so it uses each
sample four cycles after it is taken; ENERGY_SCAN does not apply to it. The
appended RSSI byte is the average over the first eight symbols after the SFD
(23.9.7, Figure 23-15).

Timer 1 channels with `T1CCTLn.RFIRQ = 1` capture on the RF interrupt
instead of their pad (SWRU191F 9.12). Model-defined input waveform, which
SWRU191F does not draw: the RF interrupt line (interrupt 16) is high while an
unmasked `RFIRQF0`/`RFIRQF1` flag stands; every RF interrupt request (23.1.1,
including the re-request when a flag is cleared while others stand) is a
rising edge and the line going low is a falling edge; RFERR does not
capture. As for pad capture, nothing is captured while Timer 1 is stopped or
in PM1-PM3, where Table 4-1 stops the system clock that drives the counter
and the input synchronizer (9.7).

## USART UART errors

UART data reaches the USART as logical frames from the host or a link, not
as pad levels. A plain byte is a well-formed frame in the receiver's format,
so it never sets UxCSR.FE or ERR and behaves exactly as before. A host frame
(`Cc2530F256::uart_receive_frame`, or the system endpoint
`device.mcu.uartN.frames`, see [system-config.md](system-config.md)) can
carry an explicit 9th bit, a wrong parity bit, a wrong first or second stop
bit, or a break:

- TX (SWRU191F 17.1.1, UxUCR): with BIT9 the 9th bit follows the data bits.
  With PARITY it is the parity of the data: D9 = 1 even, D9 = 0 odd, as
  SWRU191F words it. With PARITY = 0 the 9th bit is D9 itself. The bit does
  not depend on ORDER and is computed from UxUCR when the frame starts. Stop
  bits are always sent at the STOP level. The byte stream is unchanged.
  `uart_capture_frames` (or a subscription to `uartN.frames`) also records
  each frame with its 9th bit.
- RX (17.1.4, 17.8): the frame is checked against the receiver's UxUCR,
  latched at its start bit. ERR is set when BIT9 = PARITY = 1 and the 9th
  bit is not the expected parity. FE is set when the first stop bit is not
  at the STOP level. With SPB = 1, FE is also set one bit later, at the end
  of a wrong second stop bit, as a separate event. This is the "delay in
  setting the framing error bit" of 17.1.4.
- Model-defined: an errored frame is still received at the end of its first
  stop bit. It goes to UxDBUF with RX_BYTE, URXxIF and the URXx DMA trigger,
  or waits in the shift register on overrun. ERR and FE are set at that
  instant, before the interrupt. SWRU191F says only that the RX interrupt
  comes "when the first stop bit is checked OK" and that FE/ERR mark a "byte
  received with" the error.
- A late second-stop FE is cancelled by FLUSH, RE = 0, a mode change or a
  reset. It sets FE again even if software cleared FE from the first stop
  bit. A frame discarded by FLUSH sets no flag.
- FE and ERR are R/W0. Writing 1 keeps them and writing 0 clears them. Any
  CPU read of UxCSR clears both ("cleared on a read of the UxCSR register or
  bits in the UxCSR register"). That includes a byte read, a bit read of
  the bit-addressable U1CSR (`MOV C,U1CSR.4`), and the read of
  a read-modify-write such as `ANL U0CSR,#n`. Side-effect-free debug reads
  (`mem.read`) do not clear them.
- No register reads back the received 9th bit (SWRU191F has none).
- Model-defined: a 9th bit sent to a receiver with BIT9 = 0 is sampled as
  that receiver's first stop bit, and the sender's first stop bit as its
  second. A frame always takes the receiver's frame time.
- Break (model-defined; SWRU191F describes no break handling): the line
  stays at the start-bit level for one frame time. Data, 9th and stop bits
  are all at the START level, so the byte is `START ? 0xff : 0x00`, FE is
  set, and ERR is set when the parity of that byte disagrees with the
  START-level 9th bit (for example odd parity with START = 0).

The D9 polarity needs hardware evidence. TI design note DN112 (SWRA222B)
labels it the other way round. Delivering an errored frame (URXxIF and DMA)
also needs hardware evidence.

## USART SPI

SPI mode (SWRU191F 17.2) works at pad level on the Table 7-1 pads selected
by PERCFG and P2DIR.PRIP0, so a system's nets carry the SPI signals:

- Master (UxCSR.SLAVE = 0): writing UxDBUF starts a byte. SCK toggles every
  half bit of the baud-rate generator (17.4, equation 3), and each of the 16
  edges is a scheduled event at its own 32 MHz cycle. MOSI follows
  UxGCR.CPOL/CPHA/ORDER, and MISO is sampled from the pad level on the
  sampling edge. A net from MO to MI therefore loops each byte back
  unchanged. The byte still ends 8 bit periods after it starts. UTXxIF and
  the UTXx DMA trigger fire at the start. TX_BYTE, the received byte in
  UxDBUF, URXxIF and the URXx DMA trigger come at the end.
- Slave (UxCSR.SLAVE = 1): SCK, SSN and MOSI are pad inputs. While SSN is
  low, SCK edges sample MOSI and shift the transmit byte out on MISO. While
  SSN is high, MISO is 3-state and edges are ignored. After 8 bits the slave
  sets RX_BYTE, URXxIF and the URXx DMA trigger. ACTIVE follows the
  asserted SSN.
- A host callback (`Cc2530F256::set_spi_device`) replaces the pads with a
  byte-level exchange for the master.

The rules that SWRU191F leaves open are marked "Model-defined" in
`emulator/src/mcs51/cc2530_usart.cpp`. They cover MOSI before the first
edge, transmit buffering in the slave, SSN released mid-byte, and the PM1-3
behaviour. The model does not reproduce the CPHA = 1 back-to-back DMA
corruption (17.2.1) or the data-sheet maximum SPI rate.

## Debug interface

`cc2530_debug.cpp` models the two-wire debug interface of SWRU191F chapter 3.
It is unrelated to `debugger:`, `--until-pc` and `set_breakpoint()`, which
are the emulator's own checkpoints and never touch the chip.

**Entry and RESET_N.** `Cc2530F256::set_reset_pin(false)` (or a low
`RESET_N` net) resets the chip (`SLEEPSTA.RST = 01`) and holds it: no
instruction executes, time runs, pads see no events. The release starts the
CPU at `0x0000`, or, if DC (P2.2) fell at least twice while RESET_N was low,
enters debug mode with the CPU halted at `0x0000` (3.1).
`debug_if_enter()` performs that sequence in one call. Debug mode ends at the
next power-on or RESET_N reset, or when the chip enters PM2/PM3 with
SOFT_POWER_MODE cleared (3.5). Model-defined: a watchdog or clock-loss reset
keeps debug mode, its configuration and breakpoints.

**DC/DD wire (3.2).** In debug mode P2.2 is the DC input and P2.1 is DD,
whatever the port registers say, and neither raises port interrupts or
capture edges. The chip samples DD on falling DC edges, MSB first. After the
last input byte the chip drives DD low when the response is ready and high
when it is not; the debugger then gives 8 more DC clocks and samples again
(Figures 3-3, 3-4). With DD low, each rising DC edge shifts out the next
response bit, which the debugger samples while DC is high. After the last
bit DD is 3-state again. Model-defined:

- DD changes only at DC falling edges, so it is stable whenever it is sampled.
- No minimum clock period: a byte is processed at the DC edge that completes
  it, or at the next instruction boundary if an instruction is executing.
- DC/DD timing parameters (setup, hold, the 1/f_DC limits) are not checked.

Another emulated MCU or a host driving the nets can therefore program the
chip.

**Host port (model-defined).** `debug_if_submit()`, `debug_if_take_response()`
and `debug_if_command()` deliver whole commands without the pads. Bytes
arrive one every 128 cycles (DC at 2 MHz), and the response is due at the
last input byte (STEP_INSTR: after the stepped instruction). The host port
and the wire are exclusive: the host port refuses a command while the wire is
in the middle of one.

**Commands (Table 3-1).** The three LSBs are don't care, except the
DEBUG_INSTR byte count `yy` and the BURST_WRITE length `kkk`.

| Command | Byte | In | Out | Model |
| --- | --- | --- | --- | --- |
| CHIP_ERASE | `0x10` | 1 | status | Accepted only when no command other than READ_STATUS has been issued since entry; a refused or undefined command counts. The flash controller erases the whole main flash, lock bits included, in 20 ms (2.2.3); the information page is kept. CHIP_ERASE_BUSY and `FCTL.BUSY` are set meanwhile. |
| WR_CONFIG | `0x18` | 2 | status | Configuration byte (Table 3-2), bits 5, 3, 2, 1. |
| RD_CONFIG | `0x20` | 1 | config | Reset value `0x26` (SOFT_POWER_MODE, DMA_PAUSE, TIMER_SUSPEND). |
| GET_PC | `0x28` | 1 | 2 | PC, high byte first. |
| READ_STATUS | `0x30` | 1 | status | Table 3-3. |
| SET_HW_BRKPNT | `0x38` | 4 | status | Byte 1: number (bits 5:4), enable (3), bank (2:0); then address bits 15:8, 7:0. |
| HALT | `0x40` | 1 | status | Halts at the next instruction boundary; in PM1-PM3 it wakes the chip halted (3.5). |
| RESUME | `0x48` | 1 | status | Needs a halted CPU; the first instruction ignores breakpoints. |
| DEBUG_INSTR | `0x51`-`0x53` | 2-4 | A | Needs a halted CPU; see below. `yy = 0` is undefined. |
| STEP_INSTR | `0x58` | 1 | A | Needs a halted CPU; one instruction, or the entry of a pending interrupt, in its own cycle time; breakpoints are ignored. |
| GET_BM | `0x60` | 1 | 1 | `FMAP & 7`. |
| GET_CHIP_ID | `0x68` | 1 | 2 | CHIPID (`0xa5`), CHVER (`0x00`), the XREG values. |
| BURST_WRITE | `0x80`-`0x87` | 2 + n | status | n = `kkk`:byte 2 (0 means 2048). Each data byte is written to DBGDATA (`0x6260`, read-only to the CPU) and raises DMA trigger 31 (DBG_BW) when it arrives. |

Commands are refused, in this order:

1. undefined commands;
2. anything except READ_STATUS and GET_CHIP_ID during a chip erase;
3. anything except CHIP_ERASE, READ_STATUS and GET_CHIP_ID while
   DEBUG_LOCKED is set (3.4.1);
4. anything except READ_STATUS, HALT and GET_CHIP_ID in a power mode. 3.5
   only says "a reduced set of commands", so this set is model-defined;
5. RESUME, DEBUG_INSTR and STEP_INSTR on a running CPU.

Model-defined: a refused command shifts out the status byte in every output
byte, and `accepted` is false on the host port.

**DEBUG_INSTR.** The real core executes the 1-3 instruction bytes at the
halted PC with interrupts withheld. The model places the bytes in the CODE
view in use for that one instruction and then restores the view. A MOVC
reads memory, not the patched bytes.

The PC does not change unless the instruction transfers control (a jump,
call, return or taken branch), as with an LJMP that sets the PC. A
pre-existing interrupt request is posted again afterwards. The response is A
after the instruction.

Model-defined:

- DEBUG_INSTR takes no virtual time.
- It is not counted in `registers().instructions`, only in
  `diagnostics().debug_instructions`.
- `0xa5`, the undefined MCS-51 opcode, is not executed.

**Halting and time.** While the CPU is halted (or RESET_N is low), `run()`
executes nothing but still advances virtual time to its cycle limit or to the
next event. The peripherals follow the configuration byte (Table 3-2):

- TIMERS_OFF stops Timer 1, 3 and 4 in debug mode.
- TIMER_SUSPEND stops them while the CPU is halted, but not during a
  STEP_INSTR.
- DMA_PAUSE holds all DMA arbitration in debug mode, halted or not. The
  triggers are kept and served when it is cleared.

The sleep timer, watchdog, MAC timer and radio keep running (model-defined
scope). `Cc2530RunResult::debug_halted` and `reset_held` report the state at
the return, and `diagnostics().debug_halted_cycles` and `reset_pin_cycles`
the time spent in it.

**Hardware breakpoints (3.3.3).** There are four, set with SET_HW_BRKPNT. A
breakpoint halts the CPU before the instruction at its address and sets
HALT_STATUS. Model-defined: the 3-bit bank is compared with FMAP only for
addresses `0x8000`-`0xffff`, since the lower half is the common bank 0.

The fast path stops the engine at a single enabled breakpoint address and
single-steps when several are enabled. The halt is checked at every
instruction boundary, including the one that closes a `run()` call. Fast,
step and trace modes therefore halt at the same instruction and cycle.

**Status byte (Table 3-3).**

- PCON_IDLE and PM_ACTIVE follow Table 3-4: `10` while a PCON.IDLE request is
  settling, `11` in a power mode. The model wakes instantly, so `01` never
  appears.
- OSCILLATOR_STABLE is clear in PM1-PM3.
- STACK_OVERFLOW is model-defined. It is set when DATA `0xff` changed since
  the last check or SP is `0xff`, and stays set until reset.

**DBGLOCK (3.4.1, Table 3-5).** DBGLOCK is bit 7 of flash `0x3ffff`, the
last byte of the lock-bit page; 0 locks. The interface reads it at every
reset, because SWRU191F says the device must be reset after the bit changes.
DEBUG_LOCKED reports that latched value.

A locked chip accepts only CHIP_ERASE, READ_STATUS and GET_CHIP_ID.
CHIP_ERASE clears all lock bits, and the interface unlocks at the next reset
or debug entry.

PAGELOCK bits are enforced by the flash controller (`FCTL.ABORT`). The
lock-bit page has no PAGELOCK bit. It is write- and erase-protected outside
debug mode (2.2.3) and writable in debug mode, which is how a debugger sets
the lock bits.

**CC-Debugger-style programming.** `cc2530_debug_program()`
(`mcs51emu/cc2530_debug_programmer.hpp`) programs an image through any link:
`cc2530_debug_if_link(chip)` on a stand-alone chip,
`Simulation::debug_if_program()` / RPC `debug_if.program` in a system, or
`mcuemu run --program-via-debug-if`. It uses the chip's own mechanisms only:

1. Enter debug mode, CHIP_ERASE, then poll READ_STATUS until
   CHIP_ERASE_BUSY clears.
2. Enter again, so the cleared DBGLOCK takes effect. Check GET_CHIP_ID, then
   WR_CONFIG `0x22`, which clears DMA_PAUSE.
3. With DEBUG_INSTR, select the 32 MHz crystal (CLKCONCMD `0x80`) and set up
   two DMA descriptors:
   - DBGDATA to a 2 KiB XDATA buffer on DBG_BW;
   - the buffer to FWDATA on FLASH (trigger 18).
4. For each 2 KiB page that is not all `0xff`, in ascending order so that
   the lock-bit page comes last (with `debug_lock` it carries DBGLOCK = 0):
   1. arm channel 0, then BURST_WRITE 2048 bytes and wait for DMAIRQ;
   2. set FADDR, arm channel 1 and start `FCTL.WRITE`, then poll
      `FCTL.BUSY`.
5. Read every page back with DEBUG_INSTR MOVX through the `MEMCTR.XBANK`
   window (unless `verify` is off).
6. Pulse RESET_N without DC edges, so the firmware runs (unless `run` is
   off).

Nothing is copied into the flash array directly.

## Not modeled

- Flash wait states, prefetching and cache effects on instruction timing,
  and interrupt latency beyond the 7-cycle minimum (see the timing contract).
- Debug interface: electrical DC/DD timing (setup, hold and minimum clock
  periods), debug-mode power modes beyond the status bits, and the
  "suspended during debug instructions" timer case (DEBUG_INSTR takes no
  time). See [Debug interface](#debug-interface) for the model-defined rules.
- The real flash content after a reset or power loss during a page erase,
  chip erase or word write, and after breaking the SWRU191F 6.2.2 write
  limits: SWRU191F does not specify it, so the outcomes are model-defined and
  seeded (see "Flash fault injection"); the default abandons the operation.
- Oscillator start-up and stabilisation times, and the CPU slowdown on the
  RC oscillator or a lower CLKSPD.
- Radio observation outputs (OBSSEL pads drive low), TX test modes and
  per-frame correlation values.
- The sleep-timer STCC 5-tick margin and the MAC timer offset on the RC
  oscillator.
- USART: the CPHA = 1 back-to-back DMA corruption, sub-bit flush timing and
  the data-sheet maximum SPI rate. UART frames are logical (host and link),
  not pad levels. A link does not compare START/STOP/SPB between its ends.
  An 8-bit sender's frames reach a 9-bit receiver well formed, without the
  frame misalignment real hardware would show.
- Analog non-idealities (comparator offset, ADC noise and INL/DNL).

Rules that need hardware evidence before they can be called accurate: the
watchdog resume point after PM1-PM3, the RSSI update rate and sample instants,
the exact clock-loss time-out, the RF interrupt capture waveform, the
`IRCON` bit 6 wake from PM1/PM2, AES key/IV load interrupts (taken from recorded
`cc2530-zigbee` hardware observations, not SWRU191F), the RSSI offset (73 dB
from the SWRU191F 23.10.3 example and SWRS081; the SWRU191F CCACTRL0
description says about 76), the
priority-blocked IDLE wake, and the wake ordering of interrupts asserted at
the PCON write.

## Load warnings

Programming flash at or above `0x3e800` (the `cc2530-zigbee` NV pages and the
lock page) loads but is reported as a load warning. Programming the lock bits
also warns: PAGELOCK bits are enforced by the flash controller, and DBGLOCK
by the debug interface from the next reset (a directly loaded image is
followed by a power-on reset, so it takes effect at once).

## Flash fault injection

Everything in this section is opt-in. With the defaults (`report`,
`abandon`, SRAM fill 0, no cuts) flash, SRAM and timing behave exactly as
before; only the new counters count. The API is on `Cc2530F256`
(`set_flash_fault_config`, `power_cut`, `schedule_power_cut`,
`add_flash_trigger`, `flash_log`/`take_flash_log`, `flash_image`,
`restore_flash`), the counters are in `Cc2530Diagnostics`, and the system
layer exposes it as the `flash:` key and the `<mcu>.power` endpoint
([system-config.md](system-config.md)).

Pseudo-random choices use `draw(seed, stream, index) = mix(mix(seed ^
mix(stream)) + index)`, where `mix` is the splitmix64 finalizer (add
`0x9e3779b97f4a7c15`, then `x ^= x >> 30; x *= 0xbf58476d1ce4e5b9; x ^= x >>
27; x *= 0x94d049bb133111eb; x ^= x >> 31`). Every page erase and word write
started since the load (including ones aborted by PAGELOCK) gets the next
operation serial, starting at 1; the serial is the stream of that operation's
draws. The same seed and the same program give the same flash, SRAM and log;
another seed gives other values.

### SWRU191F 6.2.2 write limits

SWRU191F 6.2.2 allows, between two erases of a page, a 0 to be written at
most twice to a bit, a 32-bit word to be written at most 8 times and a page
at most 1024 times; otherwise "the state of any bit of a 32-bit flash word is
nondeterministic". The model tracks, per page since its last completed
erase: two bit masks per word (bits that had a 0 written once / twice), a
write count per word and a write count per page. Every word write counts,
whatever its data, and every 0 in the data is a 0 written to that bit even
if the bit is already 0. A write that is the third 0-write to any of its
bits, the 9th write to its word or the 1025th write to its page counts once
in `flash_bit_limit_violations`, `flash_word_limit_violations` or
`flash_page_limit_violations` respectively and sets the matching flag in its
log entry. The image given to `load_firmware`/`load_flash`/`restore_flash`
counts as freshly erased. Aborted (locked) and abandoned writes do not count;
partial and forced ones do. A partial erase does not restart the tracking.

`Cc2530FlashFaultConfig::limit_policy`:

- `Report` (default): violations are only counted; programming stays the
  deterministic AND of SWRU191F 6.2.
- `Nondeterministic` (model-defined fault injection, not hardware-accurate):
  the violating word becomes the low 32 bits of `draw(seed, serial, 32)`
  instead of `old AND data`.

### Interrupted erase and word write

A reset (watchdog, `reset()`, a `Reset` trigger) or a power cut while a
page erase (20 ms = 640000 cycles) or a word write (20 us = 640 cycles) is
in flight ends it with `Cc2530FlashFaultConfig::interrupted` (SWRU191F does
not say what such a cut leaves; all three outcomes are model-defined).
`elapsed` is the operation time that had passed, in cycles of the 32 MHz
base:

- `Abandon` (default): no flash change.
- `Partial`: erase: each 0 bit of the page (index `b = 8 * byte offset +
  bit`) becomes 1 when `draw(seed, serial, b) % 640000 < elapsed`. Word
  write: each bit that the write changes (`old XOR target`, where target is
  `old AND data` or the nondeterministic value) takes its target value when
  `draw(seed, serial, bit) % 640 < elapsed`. So a fraction `elapsed / time`
  of the bits lands on average, the same bits for the same seed.
- `Complete`: the full effect (logged as `forced`), counted like a completed
  erase or write.

A debug-interface CHIP_ERASE (20 ms, [Debug interface](#debug-interface))
cut the same way gets the same outcome over the whole 256 KiB main flash
(bit index `b = 8 * flash offset + bit`, logged as `chip-erase`); a
completed or forced one counts as an erase of every page. CHIP_ERASE gets an
operation serial but does not advance flash triggers, which count firmware
page erases and word writes.

A write sequence waiting for FWDATA bytes has no operation in flight, and a
word buffered behind FULL or the write phase of ERASE+WRITE never starts. The
erase or word write is logged with its outcome, the cut kind, the reset
cause, `elapsed` and the number of flash bits it changed.
`flash_interrupted_erases`/`flash_interrupted_writes` count every cut
operation, whatever the outcome; `flash_page_erases[]` counts erases applied
in full and `flash_page_writes[]` word writes applied (also partially).

### Power cuts

`power_cut()` models the supply dropping and returning at once: the flash
operation in flight gets its interrupted outcome, the 8 KiB SRAM (XDATA
`0x0000`-`0x1fff`, which includes IDATA) loses its content, `power_cuts` and
`last_power_cut_cycle` are updated and the chip comes out of a power-on reset
(`SLEEPSTA.RST = 00`, SWRU191F 4.3). Flash, the information page and virtual
time are kept. `reset()` keeps SRAM and reports `RST = 01`. SWRU191F 4.6
promises SRAM retention only through PM1-PM3, so the content after a power
loss is model-defined. After any power-on reset SRAM holds
`Cc2530FlashFaultConfig::sram_fill`, either a byte (default 0, the earlier
behaviour) or, with `nullopt`, seeded bytes. In the seeded case, 8-byte group
`i` is `draw(seed, 0x5352414d00000000 + N, i)` stored little-endian, where `N`
is the number of power-on resets since the load before this one.

Injection points, all kept across resets and loads (model-defined timing):

- `schedule_power_cut(cycle)`: at the first instruction boundary at or after
  that chip cycle (counted from the last load or power-on reset), in every
  power mode; a CPU stalled by a flash operation is cut at the exact cycle.
- `add_flash_trigger({op, nth, page, delay_cycles, action})`: on the nth
  start of a page erase or word write (counted from when the trigger is
  added, locked pages excluded) matching `op` (any, erase, write) and
  `page`, the action (`PowerCut`, or `Reset` = an external reset, RST = 01)
  fires `delay_cycles` of HF time after that start. A delay at or past the
  operation time lets it complete first. Each trigger fires once. A trigger
  armed when a load or power-on reset restarts time is dropped.

A pending cut keeps `may_wake()` true, so a sleeping chip with a cut ahead
is not reported as stuck. Several faults at one boundary act once; a power
cut wins over a reset.

### Instrumentation

`Cc2530Diagnostics` counts per page `flash_page_erases[128]` and
`flash_page_writes[128]` (since the load). With
`Cc2530FlashFaultConfig::log` set, every erase and word write (completed,
aborted, abandoned, partial, forced) is appended to `flash_log()` as a
`Cc2530FlashLogEntry` (cycle at which the outcome was decided, op, physical
address, page, outcome, cut, reset cause, elapsed cycles, changed bits,
violation flags). `FlashController::record_erase(first_page, count, op,
outcome, elapsed)` is the one bookkeeping entry for any erase path (chip
erase included). `mcuemu run --model CC2530F256` prints
`flash-limit-violations: bit= word= page=` and `flash-interrupted: erases=
writes=` when any of them is nonzero.

`tests/mcs51/test_cc2530_flash_powercut.cpp` (`cc2530emu-flash_powercut-tests`)
pins `draw` with golden values and checks each limit at its boundary under
both policies, erases and CPU and DMA word writes cut by a reset and by a
power cut at several fractions with exact seeded bytes, determinism, the
triggers, the reset cause, the SRAM fill, the image round trip, the counters
and log, and a hand-assembled program cut mid-erase that reboots and reads
the result (that program in fast, step and trace modes).
`tests/sim/test_cc2530_flash.cpp` (in `simcore-tests`) covers the `flash:`
key, the log file, the power endpoint and the persistence file.

## Core options

The model sets generic `UC_ARCH_MCS51` registers that default to the
classic 8051 behaviour for other parts (CA51F253L3 is unaffected):

- `UC_MCS51_REG_XDATA_PAGE_SFR = 0x93` (MPAGE) for `MOVX @Ri`.
- `UC_MCS51_REG_TIMER0_INTERRUPT = 0`: IE.1/TCON.5 are the CC2530 ADC
  interrupt, which has its own priority group and polling position, so the
  model posts it like every other source.
- `UC_MCS51_REG_DPS_SFR/DPL1_SFR/DPH1_SFR = 0x92/0x84/0x85` enable the second
  data pointer.
- `UC_MCS51_REG_POST_RETI_RULE = 1` enables the one-instruction-after-RETI rule.
- `UC_MCS51_REG_CYCLE_MODEL = UC_MCS51_CYCLE_MODEL_CC253X` selects the
  SWRU191F Table 2-3 cycle counts and the 7-cycle interrupt entry.
- Each request is posted with `UC_MCS51_REG_IRQ_LEVEL` (0-3) before
  `UC_MCS51_REG_IRQ_VECTOR`; the core keeps the in-progress levels in
  `UC_MCS51_REG_INTERRUPT_LEVELS` and the post-RETI state in
  `UC_MCS51_REG_INTERRUPT_INHIBIT`. Both, and
  `UC_MCS51_REG_INTERRUPT_IN_SERVICE`, are cleared on reset, so a reset during
  an ISR returns the core to its power-on interrupt state.

The CPU snapshot (`0x0004_0000`) adds DPL1 (`0x2c`), DPH1 (`0x2d`), DPS
(`0x2e`), the in-progress level mask (`0x2f`), the posted vector (`0x30`, u16)
and level (`0x32`) and the post-RETI inhibit (`0x33`).

## Tests

`tests/mcs51/test_cc2530f256.cpp` (the `cc2530emu-tests` binary) covers reset values,
all eight FMAP banks, cross-bank calls, XBANK independence, SRAM/IDATA/MPAGE/SFR
aliases, XMAP execution, interrupts in banked code with RETI, priority groups
and polling order, EA gating, dual DPTR, four-level nesting and preemption,
the post-RETI instruction rule, reset during an ISR, PCON idle, clock registers,
XREG/chip ID/info page, unsupported-behaviour errors, trace versus fast-path
state equivalence, breakpoints and Intel HEX extended addresses.
`tests/mcs51/test_cc2530f256_r2.cpp` (`cc2530emu-r2-tests`) pins the cycle
contract per opcode and checks virtual-time event delivery, the
`ENCIF_0/1` and `RFIF_0/1` flag paths and PCON.IDLE wake ordering in fast,
step and trace modes against independently specified traces.
`tests/mcs51/test_cc2530f256_lockstep.cpp` (`cc2530emu-lockstep-tests`) runs
identical programs with identical virtual-time events in fast, single-step
and trace modes and compares the complete machine state at synchronization
points (`--image FILE.hex` runs a firmware image without events).

Peripheral suites (white-box, `cc2530emu-<suite>-tests`), each checking
register semantics against SWRU191F and fast/step/trace equivalence:

- `timers`: Timer 1, Timer 3/4, sleep timer, watchdog, TICKSPD, PM1-PM3
  behaviour;
- `mactimer`: MAC timer counting, compare, overflow, latching, SFD capture,
  synchronized start/stop;
- `dma_flash_aes`: DMA modes, triggers, priorities and abort, flash erase,
  writes, stall and lock bits, AES modes, DMA and power modes;
- `io_analog_usart`: pads, pulls, peripheral mapping, port interrupts and
  wake, ADC, RNG, comparator, op-amp, UART timing, flow control and
  interrupts;
- `spi`: pad-level SPI master and slave in all CPOL/CPHA/ORDER modes,
  master-to-slave between two devices;
- `uart_errors`: transmitted 9th bit (even, odd and D9 data, ORDER = 1),
  ERR and FE on both stop bits, break, R/W0 writes and the clear on byte,
  bit and read-modify-write reads of UxCSR, errored frames with RX_BYTE,
  URXxIF, DMA, overrun and FLUSH, plain bytes unchanged, an ISR end to end
  in fast, step and trace modes;
- `radio`: TX, RX, filtering, source matching, ACK, CCA, collisions,
  two-device exchange over `VirtualAir`, CSP programs, slotted ACK;
- `minor_gaps`: clock-loss detector and `stop_oscillator`, the 8-symbol RSSI
  average with CCA and the appended RSSI, Timer 1 RF interrupt capture,
  `IRCON` bit 6, the watchdog in PM1-PM3.
- `debug_if`: every debug command's encoding and response, HALT/STEP/RESUME
  against free running in all three modes, hardware breakpoints in banked
  code, DEBUG_INSTR effects, BURST_WRITE with DBG_BW DMA and DMA_PAUSE,
  CHIP_ERASE timing, DBGLOCK rules, the configuration byte, DC/DD
  bit-banged through the pads, and programming round trips (host port and
  pads) that run like a directly loaded image.

`tests/sim/test_cc2530.cpp` (in `simcore-tests`) runs banked firmware through
the system layer and checks the memory windows, configuration errors, fault
and sleep states, time offsets, the debugger hit reports and debug-mode
entry and commands bit-banged over RESET_N/DC/DD nets;
`tests/sim/test_control.cpp` covers the `debug_if.*` RPC methods.
`tests/sim/test_cc2530_uart_frames.cpp` checks the `uartN.frames` tokens,
YAML events, CC2530-to-CC2530 links and the JSON-RPC surface.
`tests/cli/cli_exit_codes.cmake` (`mcuemu-cli-exit-codes`) checks the CLI exit
codes.
